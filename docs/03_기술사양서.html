1. 개요

1.1 목적

KCOC 파트너십지원부(사무국)가 「2027 국제나눔 파트너십 지원사업」 수행기관의 보고서 제출·검토, 컨설팅 일정, 예산·사업 변경, 전문가 보고서를 한 곳에서 관리하기 위한 웹 포털이다. 이 문서는 시스템을 인계받는 IT 담당자·개발자가 구조를 파악하고 운영·수정할 수 있도록 코드 기준으로 정리한 것이다.

1.2 범위

구분내용
포함웹 애플리케이션(Next.js), DB·인증·스토리지(Supabase), 파일 저장소(Cloudflare R2), 메일 발송(SMTP), 오류 수집(Sentry), 일일 백업 크론, 운영 스크립트
제외화면 사용법(사용자 매뉴얼 별도), 사업 규정 자체의 해석

1.3 사용자 · 규모

역할 (profiles.role)사용자화면 메뉴
admin사무국 (파트너십지원부)통합 대시보드, 자료 제출·검토, 연간 사업 일정, 컨설팅 일정, 예산변경/사업변경, 최종 자료실, 참여 기관, 공지사항, 활동 로그, 계정 관리, 사업 설정 (11개)
org수행기관 담당자내 사업 현황, 자료 제출, 연간 사업 일정, 컨설팅 일정, 예산변경/사업변경, 공지사항 (6개)
expert성과관리위원 · 컨설턴트자료 제출, 컨설팅 일정 (2개)

규모: 수행기관 약 20개, 전체 계정 약 40여 개. 이 규모를 전제로 한 설계 결정(전량 로드 등)은 15장에 정리했다.

기관 이용기간은 선발연도(orgs.picked)부터 3년(picked ~ picked+2)이다. 기간이 지난 기관 계정은 로그인은 되지만 DB 정책(org_active())에 의해 데이터 읽기·쓰기가 모두 차단되고, 화면은 "이용 기간이 종료된 계정" 안내만 보여준다.

2.2 요청 흐름

흐름경로
화면 데이터 조회·저장브라우저 → Supabase REST (anon 키 + 사용자 세션 JWT) → RLS 가 역할별로 행을 거름. 서버를 거치지 않는다.
페이지 접근브라우저 → Vercel proxy.js(세션 쿠키 갱신, 비로그인 시 /login 으로) → app/page.js(서버에서 me() 로 프로필 확인) → Portal
관리 작업브라우저 → /api/admin/*, /api/zoom → 세션으로 관리자 확인 → service role 키 또는 사용자 세션으로 Supabase 호출
파일브라우저 → /api/files(경로 권한 확인, 서명 URL 발급) → 브라우저가 R2 에 직접 PUT/GET
크론Vercel Cron → /api/cron (CRON_SECRET) → Supabase(덤프) · R2(복사)
핵심 보안 경계는 Supabase RLS 다. 화면 코드는 "RLS 가 걸러주므로 다 읽는다"는 전제로 작성되어 있어, 권한 변경은 반드시 supabase/schema.sql 의 정책으로 한다(화면에서 숨기는 것은 보안이 아니다).

4.1 사업 설정 (settings) 동작

lib/config.js 의 값은 기본값이다. 관리자 화면 "사업 설정"이 settings 테이블(한 행 jsonb)에 저장하면, loadDb()·/api/zoom 이 읽을 때 applySettings() 로 덮어쓴다(ES 모듈 live binding).

settings.data 키의미
program, team, program_year사업명, 부서명, 사업연도(차년도 계산 기준: 차년도 = 사업연도 − 선발연도 + 1)
reports기관 보고서 종류·마감 [{key,label,start,due}]. 기본 mid/result/final. key 는 DB 에 저장되므로 변경 금지
fix_days, cap수정 요청 기한(기본 7일), 컨설팅 일자별 확정 정원(기본 2)
consult_types컨설팅 회차 [{key,label,required,mode,slots}]. 기본 h1/h2(일시 선택) · opt(신청서 방식)
expert_reports전문가 보고서 종류·마감
notices공지사항 목록
mail_subject, mail_body확정 안내 메일 템플릿. 자리표시자 {기관명} {담당자} {차년도} {회차} {일시} {링크} {부서} {사업명}

코드 상수(설정 화면에서 못 바꿈): MAX_MB(R2 사용 시 200, 아니면 50), APPROVAL_THRESHOLD 1천만 원, CHANGE_LIMIT 0.2(당해년도 예산 대비 누적 변경 한도), BUDGET_LEVELS, 선택컨설팅 신청서 항목 OPT_FIELDS.

5.1 컨설팅 일정 흐름 (테이블 관점)

  1. 관리자가 회차별 후보 일시 등록 → settings.data.consult_types[].slots
  2. 전문가가 가능 일시 체크 → expert_avail (추가 가능 시간은 expert_notes)
  3. 관리자가 기관별 담당 전문가 배정 → orgs.expert_id
  4. 기관이 담당 전문가의 가능 일시 중 희망 순위 선택 → avail. 같은 전문가를 공유하는 다른 기관의 선택·확정은 "선점"으로 표시
  5. 관리자 확정 → confirms + alerts, Zoom 링크 입력 시 /api/zoom 이 안내 메일 발송
  6. 선택컨설팅(opt)은 기관이 신청서(consult_apps)를 내고 사무국이 전문가·일시를 배정

5.2 보고서 제출 흐름

기관이 파일을 org-{id}/{kind}/v{no}/ 에 올리고 versions 에 행 추가, submissions.status 를 submitted 로 갱신 → 관리자가 검토(reviewing), 의견(feedbacks), 수정 요청(revision, due_fix), 최종 승인(approved, alerts 생성). 화면의 제출 목록은 활성 기관 × REPORTS 조합으로 만들어지며, DB 에 행이 없으면 "미제출"로 보인다.

6. 권한 모델

모든 public 테이블에 RLS 가 켜져 있고, 정책은 public 50개 + storage 3개다. 모든 정책은 to authenticated 이므로 로그인하지 않은(anon) 요청은 아무 행도 읽거나 쓰지 못한다.

DB 의 파일 경로에 r2: 접두어가 있으면 R2, 없으면 Supabase files 버킷에 있는 파일이다.

7. 서버 API

모두 app/api/**/route.js. 인증은 Supabase 세션 쿠키(me() 또는 serverClient().auth.getUser())로 확인한다. proxy.js 는 /api 를 거치지 않으므로 각 라우트가 직접 권한을 확인한다.

엔드포인트권한요청동작
POST /api/admin/usersadmin{email, password, role, orgId?, name, title}service role 로 Auth 사용자 생성(이메일 확인 완료 상태) → profiles 삽입. 프로필 삽입 실패 시 생성한 사용자 삭제(롤백). org 는 orgId 필수

8. 파일 저장 · 다운로드

8.1 업로드 (lib/db.js uploadFiles)

  1. 화면(Uploader)이 파일 선택·크기 검증(MAX_MB: NEXT_PUBLIC_R2 가 있으면 200MB, 없으면 50MB)
  2. 경로 {prefix}/{Date.now()}-{파일명} 로 /api/files 에 op: put 요청
  3. 응답 503(R2 미설정) → Supabase files 버킷에 직접 업로드, 경로 그대로 저장
  4. 응답 URL → 브라우저가 R2 에 직접 PUT (Vercel 을 거치지 않으므로 함수 본문 크기 제한 없음), 경로를 r2:{path} 로 저장
  5. 결과 [{n, s(MB), path}] 를 versions.files 또는 docs·reports 행에 기록

8.2 다운로드 (download)

경로 형태처리

10.2 DB 복원 (scripts/restore.mjs)

  1. Supabase → Storage → backups 에서 복원할 파일명 확인
  2. 실행 (파일을 내려받아 테이블별 upsert, 계정은 복원하지 않고 이메일 목록만 출력) 
    node --env-file=.env.local scripts/restore.mjs ieum-2026-09-14.json
  3. 계정이 없어진 경우 계정 관리 화면에서 재발급 후 비밀번호 재설정 안내
복원 대상은 백업 대상과 같은 18개 테이블이며, 테이블별 충돌 키는 schema.sql 의 기본키와 같다(2026-09-28 대조 확인). orgs.expert_id ↔ profiles 상호 참조 때문에 orgs 는 담당 전문가를 비운 채 먼저 넣고 마지막에 다시 채운다. 계정(auth.users)이 없는 빈 DB 에서는 profiles 가 복원되지 않으며, serial 시퀀스는 스크립트 주석의 setval SQL 로 맞춘다. 실제 복원 리허설은 테스트 프로젝트에서 한 번 해 두는 것을 권한다.

10.3 파일 복원

Cloudflare 대시보드 → R2 → ieum-files-backup 에서 해당 파일을 내려받아 다시 올리거나, 같은 키로 ieum-files 에 복사한다. DB 의 경로(r2:{key})는 그대로 쓸 수 있다.

파일 백업은 같은 Cloudflare 계정 안의 사본이다. 계정 자체 사고까지 대비하려면 주기적으로 외부(로컬·다른 클라우드)에 내려받아 둔다. Supabase 폴백 저장소(files 버킷)는 R2 미설정 때만 쓰이므로 파일 백업 대상이 아니다.

10.4 Supabase 자체 백업

무료 플랜 기준 Supabase 의 시점 복구(PITR)는 없다. 위 JSON 덤프가 주 복구 수단이다.

SUPABASE_SERVICE_ROLE_KEY서버 전용RLS 우회. 계정 발급·삭제, 기관 삭제, 크론 백업, 스크립트. 절대 브라우저에 노출 금지
NEXT_PUBLIC_R2브라우저값이 있으면 파일 상한 200MB(화면 표시용 플래그)
R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY서버 전용R2 접속. 셋 중 하나라도 없으면 R2 미설정으로 보고 Supabase 저장소로 폴백
R2_BUCKET서버 전용선택. 기본 ieum-files
SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, MAIL_FROM서버 전용메일 발송
RESEND_API_KEY서버 전용선택. SMTP 미설정 시 대체 발송
GMAIL_USER, GMAIL_APP_PASSWORD서버 전용선택. SMTP_USER/PASS 의 구 이름(호환용)
CRON_SECRET서버 전용크론 호출 인증. Vercel Cron 이 자동으로 Bearer 헤더에 넣음
NEXT_PUBLIC_ 로 시작하는 변수는 빌드 시 브라우저 코드에 들어간다. 비밀값에 이 접두어를 붙이지 말 것. 환경변수를 바꾼 뒤에는 재배포해야 반영된다.

13.1 권한 모델 E2E 검증 (scripts/e2e-check.mjs)

node --env-file=.env.local scripts/e2e-check.mjs

service role 로 임시 기관 2개(활성/만료)와 임시 기관 계정 1개를 만들고, 그 계정으로 실제 로그인해 Supabase API 를 호출한다. 끝나면 임시 데이터를 모두 삭제한다. 27개 항목을 확인하며, 운영 DB 와 schema.sql 로 새로 만든 DB 양쪽에서 전부 통과했다(새 DB 와 운영의 스키마 정의 차이 0).

14. 운영 절차

14.1 DB 구조 변경

supabase/schema.sql 은 변경 이력이 아니라 현재 최종 상태의 설치 스크립트다(변경 이력은 git 기록).

  1. 운영 DB 에는 바꿀 부분만 Supabase → SQL Editor 에서 실행 (alter table …, create policy … 등)
  2. schema.sql 도 같은 최종 상태가 되도록 해당 부분을 고친다 (뒤에 이력을 덧붙이지 말 것)
  3. 권한 검증 
    node --env-file=.env.local scripts/e2e-check.mjs
  4. 새 테이블을 추가했다면 함께 고칠 곳: app/api/cron/route.js 의 TABLES(백업 대상), lib/db.js loadDb()(화면 로드), scripts/restore.mjs 의 ORDER·PK(복원), RLS 활성화와 adm 정책
schema.sql 은 빈 프로젝트 전용이다. 이미 테이블이 있는 운영 DB 에 전체를 실행하지 말 것.

14.2 새 Supabase 프로젝트에 설치 (재구축 시)

  1. Supabase 에서 New project (리전 Northeast Asia (Seoul))
  2. SQL Editor 에 supabase/schema.sql 전체를 붙여넣고 Run
  3. Authentication → Users → Add user (Auto Confirm) 로 관리자 계정 생성
  4. SQL Editor 에서 관리자 프로필 등록 
    insert into profiles (id, role, name, title, email)
select id, 'admin', '이름', '파트너십지원부', email from auth.users where email = '관리자 이메일';
  5. Project Settings → API 의 URL · anon key · service_role key 를 Vercel 환경변수에 등록, 재배포
  6. 인증 설정(site_url, redirect URL, SMTP)을 supabase/config.toml 기준으로 적용
  7. 필요 시 백업 JSON 으로 데이터 복원(10.2)
